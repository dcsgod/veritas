The Problem

Most "fact-checking" tools skip straight to the conclusion

Ask a typical AI system a politically loaded question about an Indian public figure or controversy, and it will hand back a fluent, confident paragraph — with no visibility into which outlets said what, whether anyone disagreed, or whether the claim was ever cross-checked at all.

Veritas takes the opposite approach. Instead of producing a single narrative answer, it treats a query as a bundle of atomic, independently checkable claims. Each claim is retrieved from multiple outlets across the editorial spectrum, actively tested against sources that might contradict it, and only then assigned a grade. The verdict is a function of the evidence gathered during the run — never a template the pipeline was told to arrive at.

Design Principles

Seven rules the pipeline is built to enforce

These aren't UI copy — they're structural constraints baked into the prompts, the data model, and the audit logic at every stage.

01

No verdict before evidence

Conclusions are computed from cross-verified evidence at runtime, never hardcoded as pipeline instructions.

02

Claims vs. facts vs. opinions

These are discrete objects in the data model, not a single blended "answer" — each claim carries source attribution, outlet stance, and a calculated grade.

03

Multi-outlet triangulation

Every claim is cross-checked across outlets with differing editorial leans — left, centre, right, and international.

04

Active disconfirm search

The system deliberately searches for sources that would contradict a claim. Finding none is logged as a gap, not treated as confirmation.

05

Entity scope limit

Only public figures and organizations are profiled, strictly on-record. Private citizens are excluded from the entity graph entirely.

06

No motive attribution

Reports describe on-record actions and statements only — never inferred psychological intent or unevidenced ambition.

07

Multi-language output

English is the base reasoning language; a dedicated final pass produces a Hindi translation of the finished report.

Pipeline Architecture

Seven stages, one LangGraph state machine

A query enters as free text and exits as a graded, source-linked, bilingual report. Every stage writes into a shared state object that later stages read from — claims, entities, and timeline events accumulate rather than get regenerated.

1

Topic Decomposition

The raw query is broken into roughly six checkable sub-questions, turning one broad ask into a set of narrow, verifiable targets.

Claim Grading Matrix

Four grades, each earned differently

Grading is deliberately conservative: agreement alone isn't enough, and silence is never read as consent.

Confirmed

Corroborated as fact by two or more independent outlets spanning diverse editorial leans — for example Left + Right, or a domestic outlet plus an international one.

Disputed

Outlets explicitly contradict one another regarding the claim, and that disagreement is surfaced rather than averaged away.

Unverified

Reported by only a single outlet, or by outlets that all share the same editorial lean, or with no corroboration found at all.

Opinion

The source itself explicitly frames the statement as editorial analysis or personal commentary, not reported fact.

Tech Stack

What's actually running underneath

Orchestration
LangGraph (Python)
A StateGraph wires the seven pipeline stages together and carries shared state between them.
Backend API
FastAPI + SSE
Server-Sent Events stream stage progress to the frontend as the pipeline runs, rather than blocking on a single response.
Primary LLM
Groq — Llama 3.3 70B / 3.1 8B Instant
The 8B model handles decomposition, extraction, verification, and translation; the 70B model handles synthesis.
Fallback LLM
Google GenAI SDK
Gemini 2.5 Flash, 1.5 Flash, and 2.0 Flash are available as fallback models if the primary provider is unavailable.
Search Provider
Tavily Search API
Powers both the initial multi-outlet retrieval and the targeted disconfirm searches.
Frontend
React 18 + Vite + vis-network
A custom dark design system renders the report, timeline, and an interactive entity graph via vis-network.
Data Model

Hard Guardrails

What the pipeline is explicitly forbidden from doing

Where the design principles state intent, these guardrails are the enforcement layer — checks that run against the pipeline's own output before it's shown to anyone.

No private individual profiling

A hard filter prevents the entity graph from identifying non-public citizens, regardless of how prominently they appear in retrieved sources.

No motive inference

Phrases like "politically motivated," "secretly wants," "brand-building," and "hidden agenda" are treated as banned language and strictly audited out of generated text.

No same-lean upgrades

Multiple outlets that share the same editorial lean repeating a claim does not, by itself, upgrade that claim to Confirmed.

Explicit disconfirm gaps

Claims for which no opposing source was found are flagged as a "Disconfirm Gap" in the report — never silently assumed true.

Run It Yourself

Clone it, key it, run it

The backend is a Python/FastAPI service, the frontend a Vite-powered React app. Both run locally against three free-tier API keys.

git clone https://github.com/dcsgod/veritas.git
cd veritas

# backend — needs Python 3.10+
cd backend
python -m pip install -r requirements.txt
python -m uvicorn main:app --host 0.0.0.0 --port 8000 --reload

# frontend — needs Node.js v18+, in a second terminal
cd frontend
npm install
npm run dev

Requires a GROQ_API_KEY, a TAVILY_API_KEY, and an optional GEMINI_API_KEY for fallback, set in a root .env file. The backend health check lives at /api/health on port 8000; the frontend dev server runs on port 5173.
